# 設計ドラフト — 開発テスト環境の三層化（破壊を前提にする）

**種別**: 設計ドラフト（**未承認**）
**起草**: 2026-07-27 / Android チーム（オーナー提案を設計化）
**制度部分の所管**: **官房**（標準開発環境）。§5 を官房へ伺う。

---

## 0. なぜ変えるのか

2026-07-26〜27 に、**同じ根から出た事故が2つ**起きた。

- **「実機を触るな」と制約した** → 実装者が自分の描いた絵を一度も見ずに書き、**プレビューの描画が破綻**した（第三者2者が一致指摘）
- **「実機 adb を許可した」** → 実装者が `adb uninstall` を実行し、**実車走行の映像 約14,600枚を失った**

**触り方を慎重にする方向では解けない。** 一方に振れば品質が落ち、もう一方に振ればデータが消える。
**解は「破壊が無料で、しかも頻繁にできる場所を作ること」**である。

**もう1つの実証**: 映像が出ない不具合の原因の一つは **`Mbgl: loading style failed`＝地図パッケージが無いと chainage も映像も動かない**という
地図依存だった。**これは「地図を入れていない状態」で動かして初めて見えた**。
**多様な状態で動かさないと見えない不具合がある**——腫物に触る開発では、その状態を作れない。

> **オーナーの言葉（2026-07-27）**: 「実機をロボットが触らない分、手戻りの影響度は軽微。
> 腫物に触る開発は後の製品品質に大きくかかわってくる」

## 1. 三層（役割・データ・破壊の可否）

| 層 | 役割 | 持つデータ | 破壊 | 触る主体 |
|---|---|---|---|---|
| **VM1 開発ベッド**（エミュレータ） | 復元済みの実データで開発・動作確認 | 実データの**複製** | **しない** | エージェント可 |
| **VM2 破壊テスト台**（エミュレータ） | uninstall → 新版 install → 復元 → 検証 | **使い捨て** | **毎回する** | エージェント可 |
| **実機**（OPPO / 新機） | 完成品のデバッグ機＋**実車走行データの取得・回収** | **唯一の一次データ** | **絶対にしない** | **人間のみ** |

**データの流れは一方向**:

```
実機（実車走行で取得）
   └─ 全量バックアップ .zip ──→ VM1（復元して開発を進める）
                                    │
                              新版ができたら
                                    ↓
                              VM2（uninstall → 新版 install → .zip から復元 → 検証）
                                    │
                                 合格したら
                                    ↓
                                  実機（人間が入れる）
```

**一次データは実機にしかなく、実機は人間しか触らない。VM は `.zip` から何度でも作り直せる。**
**したがって VM 側の手戻りは構造的に「失うものが無い」。**

---

## 2. VM2 が果たす、ほかで代替できない役割

**VM2 の存在意義は「復元が本当に効くことを毎回証明すること」である。**

今日「作れるが戻せない」状態で困ったのは、**戻す試験ができる場所が無かったから**だった
（機種変更バックアップの設計ドラフト §0 参照。非目的「復元」を1日で撤回した）。
VM2 があれば、**復元は毎回自動で試される**。

**VM2 の合格条件**:
1. 新版がクリーンインストールできる
2. **`.zip` から復元でき、`manifest.json` の SHA-256 とファイル数が一致する**
3. 復元後にアプリが起動し、コース・停留所・映像が揃っている
4. **DB のマイグレーションが通る**（救出 DB は v12、現行 v17。版が上がるたびここで効く）

**副産物**: VM2 は必ず**「データなし・地図なし」から始まる**。
**これが偶然そのまま「地図依存の不具合」の検査になっている**——今日の不具合は、まさにその状態でしか見えなかった。
**明示的に検査項目として立てる**（§4）。

## 3. 実機を守る仕組み（禁止文ではなく構造）

1. **アプリ ID 分離（2026-07-27 実装済み・`63acf35`）**——`debug` は `com.istech.buscourse.debug`、
   実データを持つのは `field`（suffix 無し）。**開発の uninstall が本番データに届かない**
2. **エージェントの adb 対象から実機を外す**——委託指示書に**実機の serial を書かない**。
   `adb -s <emulator-serial>` の**明示指定を必須**にする。
   **「実機に触るな」という禁止文だけに頼らない**（官房も「禁止リストは負け筋」と認めている）
3. **実機へのインストールは人間が行う**——エージェントは APK を作るところまで

---

## 4. 「多様な状態で動かす」を運用に組み込む

地図依存バグの教訓。**4象限で動かす**。

| | 地図あり | 地図なし |
|---|---|---|
| **データあり** | VM1（通常の開発） | **← 今日の不具合はここで露見した** |
| **データなし** | 新機の初期状態 | **VM2 の開始状態（毎回ここを通る）** |

**VM2 は毎回「データなし・地図なし」から始まるので、この象限が自動的に検査される。**
残る「データあり・地図なし」は、VM1 で**地図パッケージを外した状態**を作れば足りる（データは消さない）。

## 5. 官房へ伺う点（制度部分）

1. **「ロボットは実機に触らない」を制度にするか。** 本ドラフト §3 は運用手順だが、
   **§3-2（指示書に実機 serial を書かない）は委託の作法**であり、当チーム限りにするか横断にするか。
   Windows チームも実機・USB を扱うため、横断の価値がありうる
2. **官房 CHARTER §3d「ロボットより先にバックアップ」との関係。** 本設計は §3d の具体化にあたると理解している
   （退避機構＝全量バックアップが先にでき、その `.zip` が VM への供給路になる）。**その理解で正しいか**
3. **AVD 構成は当チームの運用事項として扱ってよいか**（標準開発環境＝官房所管との境界確認）

## 6. 実装（当チームでできること）

- **VM1**: 既存 `buscourse_test` を昇格。**data パーティションを 6GB → 16GB へ拡張**
  （段階2 の検証で実際に「/data 残16MB」まで逼迫し一時領域を削る羽目になった実績がある）
- **VM2**: 新規 AVD を作る。**使い捨てなので 6GB のままでよい**（毎回消すので溜まらない）
- **画面はどちらも 1080×2400 / density 420**＝**RENO3 相当**。
  **標準はスマホの画面であり、タブレットの横広比率を設計目標にしない**（オーナー明示 2026-07-27）
- タブレット（Teclast P50Mini・Android 16・79GB空き）は、**当面「破壊を含む手動テスト台」**として併用する
  （VM2 と役割が重なるが、**実 OS・実ストレージでの確認**という別の価値がある）

## 7. 非目標

- 実機を CI に接続すること（実機は人間の領域）
- VM で実車走行データを新規に取得すること（GPS は実機でしか取れない）
- タブレットの画面比率に合わせた UI 設計（標準は RENO3 の画面）
- 実機の自動化（**そこが今回の事故の入口だった**）
