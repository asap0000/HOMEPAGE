**種別**: 設計ドラフト（**未承認**。オーナー承認＋官房の版鋳造裁定を経て設計正典へ）

**ゲート**: `design-gate` は**非該当**（画面・UI を持たないスキーマ／ロジック増分。ただし癖リストは読了。§2 に非目標、§6 に既定を置く）

## 0. 何のための設計か

2026-07-26 のデータ消失で **07-12〜07-16 のタイムラプス映像 約14,600枚**が失われた。
残るのは **07-10 の3便（映像 6,161枚＋GPS）**だが、当時は停留所カード未登録で記録したため
そのままでは映像ナビの素材にならない。**これを現行フォーマットで使えるようにする。**

**実測で確定している切れ目**（エミュレータ検証・2026-07-26）:
`course_stop.frame_id`/`event_id` が全 NULL → `NaviMapGenerator` が時刻窓を導けない →
GPS サンプル経路が選ばれず `route_point`（時刻軸なし）にフォールバック → `navi_track_point.t_rel_s` が全て 0.0 →
`navi_segment.session_id`／`base_epoch_ms` が **明示的に null** → `NaviFrameResolver` が黙って null →
「この区間の映像はありません」。加えて **`course.source_session_id` が course 6/7/8 すべて session 8**（映像消失セッション）を指している。

## 1. 原理: 空間が主・時刻は補助（オーナー指示 2026-07-27）

**旧データと現行DBを生タイムスタンプで結合してはならない。** 端末時計のずれ・タイムゾーン・記録形式の差が
静かに誤差を注入する。`base_epoch_ms + t_rel_s` は**実収録データに対する正典**であり、その規律以前の旧データに
無理に適用しない。**空間特徴でアンカリングする。**

**実測根拠（`2026-07-18_devicepull` DB・読み取りのみ）**

| 観測 | 値 | 意味 |
|---|---|---|
| `timelapse_frame` の座標保有率 | **99%**（sessions 1/2/3/8/18 すべて） | 空間アンカリングの材料が全セッションにある |
| フレーム座標→最寄り GPS 点の距離 | **中央値 0.0m** | **フレームは記録時の GPS 点をそのままコピーしている**＝空間で厳密に結べる |
| 同じペアの時刻差 | 中央値 +1〜2.4秒、**95%分位 +23〜55秒、最大 128秒** | **時刻では一意に決まらない** |

> **この時刻差の読み方（正直に）**: これは**時計のずれを証明していない**。停車中は GPS 点が同じ場所に留まるため、
> 空間で最寄り点を引くと「到着した最初の点」に当たり、フレームは停車中も撮り続けるので差が開く＝**測っているのは停車時間**。
> ただし結論は変わらない——**時刻で引くと停車区間で多対一になり一意に決まらない**。時刻は基準にできない。

**幾何は既存の列で足りる**: `navi_track_point` は `chainage_m` と `lat`/`lon` を**両方持つ**。
`timelapse_frame` も `latitude`/`longitude` を持つ。**フレーム → chainage の射影は既存列だけで計算できる**（新しい幾何列は不要）。

## 2. 設計（3つの変更）

### 2-1. 結合の産物を別テーブルへ隔離する ★最重要

**新テーブル `navi_frame_index`** を設ける。

| 列 | 意味 |
|---|---|
| `navi_map_id` | どのナビ用マップの索引か |
| `seq` | chainage 昇順の並び |
| `chainage_m` | 経路上の位置（`navi_track_point` へ射影して得た値） |
| `frame_id` | `timelapse_frame.id` |
| `lateral_offset_m` | 経路からの横方向のずれ（射影の残差。品質指標） |
| `provenance` | 出自（§2-3） |

**なぜ新テーブルか**: `timelapse_frame`／`gps_point` は**実収録テーブル**である。そこへ派生値（chainage）を
書き戻すと、**結合の産物が実測の中に混ざる**。オーナーの懸念「近似結合品が後日"実測の真実"として振る舞い始める」は
まさにこれ。**結合の産物を物理的に別テーブルへ隔離すれば、混ざることが構造的に起きない**（戸籍化のときと同じ論理）。
**実収録テーブルは一切変更しない。**

### 2-2. 映像の引き当てを2経路にする（時刻軸を汚さない）

`NaviFrameResolver` を次のように分岐させる。

1. **時刻軸が使える**（`navi_segment.session_id` と `base_epoch_ms` が揃っている）→ **従来どおり `base_epoch_ms + t_rel_s`**。実収録データの経路は変えない
2. **使えない**（旧データ）→ **`navi_frame_index` を chainage で引く**

**★`t_rel_s` を空間から逆算して合成してはならない。** 合成した時刻が実測を騙る。**2経路にすることが、時刻軸を守る方法**である。

**あわせて必要な是正**（実測で判明したもの）:
- **GPS サンプル経路の選択条件から「時刻窓が導けること」を外す。** `usesGpsSamples` が false になる唯一の理由が
  時刻窓の不在だが、**空間アンカリングでは時刻窓は不要**。ここを外すと `navi_track_point` が
  **対象セッションの実測 GPS から作られる**（`route_point`＝設計上の経路ではなく）。**フレームが経路上に厳密に乗る前提はこれ**。
- **対象セッションを明示指定できるようにする。** 現状は `course.source_session_id` 依存で、それが消失セッションを指している。

### 2-3. 出自タグ（3段）

`provenance` は2値ではなく**3段**にする。

| 値 | 意味 | 付く先 |
|---|---|---|
| `RECORDED` | 実収録。時刻軸あり | 実収録由来の `navi_segment` |
| `GEOFENCE_MATCHED` | 停留所を 50m 圏で一致させて復元した | 遡及抽出が作った `segment_track`／`navi_frame_index` |
| `FALLBACK_SYNTHESIZED` | **停留所が 50m 圏で一致せず、最近傍点にフォールバックして生成した** | 同上 |

**★`FALLBACK_SYNTHESIZED` を独立させる理由**: 実測で、`extractSegmentsForCourse` は**未一致の停留所があっても
最近傍点にフォールバックして区間を作る**ことが判明した（S8-3×session3 は **10/13 しか一致していないのに12区間できた**。
未一致の最近傍距離は 113〜131m）。**実際には通っていない場所を繋いだ区間が混じりうる**。
これを `GEOFENCE_MATCHED` と同じ札にすると選り分けられない。**将来「なぜかこの区間だけ並走検出が暴れる」の正体はここ**。

**フレーム → chainage 自体は厳密**（0.0m 一致）なので近似ではない。ただし**その索引が載っている経路が
近似で作られている**なら、索引も同じ札を継ぐ（出自は最も弱い根拠に合わせる）。

**付与先**: `segment_track` に `provenance` 列を追加。`navi_frame_index` は新設なので最初から持つ。
`navi_segment` は `media_mode`（既存列）に引き当て経路を表す値を持たせれば足り、**列追加は不要**。

## 4. 検証

**純計算（単体テスト）**
- フレームの lat/lon → `navi_track_point` への射影（chainage と横方向残差）。既知の点で厳密に一致すること
- `provenance` の決定（一致／フォールバックの分岐）
- 引き当ての2経路の選択（時刻軸あり／なし）

**実データ（読み取りのみ・エミュレータ）**
- 07-10 の3便で、フレームが **chainage 昇順に単調に並ぶ**こと
- 横方向残差の分布（大きい箇所＝経路から外れた撮影を検出できること）
- **映像が chainage 連動で切り替わること**（今回そこまで到達できていない）

**selftest（オーナーの懸念への保険）**
- **`FALLBACK_SYNTHESIZED` の区間を機械的に選り分けられること**。将来の並走検出はこれを実収録と区別して扱う

## 5. 非目標

- **`t_rel_s` の合成**（＝時刻軸の偽造）。**却下**。§2-2 のとおり2経路で解く
- **実収録データの引き当て経路の変更**。従来どおり時刻軸を使う
- **実収録テーブル（`timelapse_frame`／`gps_point`）への書き込み**。一切しない
- **#8／#18 の失われた映像の再構成**。不可能
- **アプリ内の復元機能**。別（機種変更バックアップの設計ドラフト §0 で非目的と決定済み）
- **`ExtractionScreen` の UI 配線**（未配線と判明したが別件）

## 6. 既定で守ること

- 救済作業は**すべて複製に対して行う**。`2026-07-18_devicepull`／`2026-07-10`／`I:\` の原本は読むだけ
- **実機には触らない**。検証はエミュレータのみ（データ消失事故の直後）
- 索引を作り直せること（`navi_frame_index` は再生成可能な派生物。壊しても実収録から作り直せる）
