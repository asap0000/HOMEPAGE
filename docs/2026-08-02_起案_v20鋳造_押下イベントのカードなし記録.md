# 起案: DB 版 v20 の鋳造 ── 押下イベントを「カードなし」で記録できるようにする

**種別**: 版鋳造の起案（**官房マター**・未承認） | **起案**: 2026-08-02 | **起案元**: Android チーム
**宛先**: 官房（`teams/kanbo/`） | **根拠**: CHARTER §5（版鋳造は官房へ上げる4点のひとつ）

---

## 0. 要旨（先に結論）

**`stop_visit_event.stop_card_id` を NOT NULL → NULL 許容にする版 v20 の鋳造をお願いしたい。**

- **これが無いと、POC で録った走行からコースが1件も作れない**（実データ・実機で確認済み・§2）。
- **読み手側は既に対応済み**。コース創設パス1 は「カードなしの MANUAL イベント」を想定して書かれており、
  **コード変更は不要**。**書き手を塞いでいるのが NOT NULL 制約だけ**（§3）。
- **影響は1箇所のみ**。非null を前提にしているコードは**デッドコード内の1箇所だけ**（§4）。
- **あわせて報告**: **v18 予約の前提が崩れている**（実機が既に v19 に到達済み・§6）。
  これは 2026-07-30 の官房裁定が置いた前提と食い違うため、**v20 とは別に裁定が要る**と考える。

---

## 1. なぜ今か（「測ってから鋳造する」は満たされたか）

STATE の方針は **「v20 は POC の実測が出てから起案する（測ってから鋳造する）」**だった。実測は出た。

| 走行 | 内容 | 結果 |
|---|---|---|
| 実走1回目（#1〜#8） | テストコース1周3.4km×8本 | 押下82件・**100%記録・位置null 0件** |
| 実走2回目（#12〜#16） | 同コース | 押下36件・**恒等式すべて成立**・GPS欠測 0.0% |

**玄関（押下を確実に残す）は立証された。** 次は「残した押下をコースへ繋ぐ」段階＝POC 段階2 であり、
そのために必要な唯一のスキーマ変更が本件である。

## 2. 今どうなっているか（実データ・実機で確認済み）

**コース創設は POC で録ったセッションに対して構造的に空振りする。**

コース創設パス1 の一次素材は次の2つだけ（`CourseRepository.kt:1769` `generatePass1RawStops`）:

1. **マーカー付き LORES フレーム**（`timelapse_frame.stop_card_id IS NOT NULL`）
2. **`stop_visit_event`（`trigger_type='MANUAL'`）**

**POC の玄関は、設計どおり意図的にどちらも書かない。**

- `stop_visit_event` へは一切書かない（**書けない**——`stop_card_id` が NOT NULL で、押下時点ではカードが未定のため）
- LORES に `stop_card_id` タグも付けない（**付けられない**——同上。記録時の吸着は誤吸着事故を受けて廃止済み）

**実データ**（実走2回目の複製DB）:

| セッション | 全 LORES | マーカー付き LORES | MANUAL イベント |
|---|---|---|---|
| #12 | 580 | **0** | **0** |
| #16 | 101 | **0** | **0** |

**実機**: #12（LORES 580枚・押下13件・GPS完全）をコース創設で開くと
**「合計: 0 件」「断片がありません。」創設ボタン無効**。理由の説明は無い。

> **⚠ 押下データ自体は消えていない**——`poc_press_log.jsonl` に座標つきで全件残っている。**繋ぎ込みが無いだけ**。
> ただし**画面上の見え方は 7/12 以来の「押しても何も残らない」と区別がつかない**。

**迂回路も無い**: パス3（停車推定）は解析と速度マップ表示まで実装済みだが**格上げが未実装**。
仮に実装しても #12 で拾えるのは**押下13件中4件だけ**（実測「完全停止は18%のみ」と整合）＝**押下の代替にならない**。

## 3. 何を変えるか（最小の1列）

```kotlin
// core/data/RecordingEntities.kt  StopVisitEventEntity
@ColumnInfo(name = "stop_card_id") val stopCardId: Long,   // 現在
@ColumnInfo(name = "stop_card_id") val stopCardId: Long?,  // v20
```

- **外部キーはそのまま残す**（`ForeignKey(... onDelete = RESTRICT)`）。SQLite は NULL を FK 違反にしないため、
  「カードが決まっていれば必ず実在するカードを指す」という保証は失われない。
- **索引もそのまま**（`Index("stop_card_id")`）。
- マイグレーションはテーブル再作成（SQLite は列の NOT NULL 解除を ALTER でできないため。
  既存の `MIGRATION_10_11` / `MIGRATION_11_12` と同じ手法で前例がある）。

**★読み手の変更は不要**。コース創設パス1 は**もともとカードなしイベントを想定して書かれている**:

```kotlin
// generatePass1RawStops（既存）
cardId = null, // 記録時の誤吸着（event.stopCardId）は無視する。frame由来点と扱いを揃える
```

パス1 は `event.stopCardId` を**読まずに捨てている**。カードの判定は一律パス2（真の位置から探し直す）に
委ねる設計が 2026-07-16 に確定済みで、**その設計が v20 を先取りしていた**。
`stop_card_id` が NULL でも `lat`/`lon` があれば点が立つ。**書き手を塞いでいるのが NOT NULL 制約だけ**である。

## 4. 影響範囲（実測）

`stop_visit_event.stopCardId` を非null前提で扱っているコードを全走査した。**該当は1箇所のみ**:

| 箇所 | 内容 | 状態 |
|---|---|---|
| `CourseRepository.kt:2088-2091`（`extractSegmentsFromSession` 内） | 到着イベント列を `stopCardId` で畳む | **デッドコード**（呼び出し元 `ExtractionScreen` は MainActivity から到達不能） |

- **AUTO 検知経路**（`captureAndRecordStopVisit`）は**カードを持って書く**ので v20 の影響を受けない
  （AUTO は退役決定済みだが実装は残存。今回は触らない）。
- **既存データへの影響なし**。NOT NULL → NULL 許容は制約の緩和であり、既存行はすべて有効なまま。
- **機種変更バックアップ**への影響なし（`SCHEMA_VERSION` を参照するのみ）。

## 5. 検討して採らなかった代案

| 代案 | 却下理由 |
|---|---|
| **押下時にカードを自動生成する** | 押下ごとにカードが増え、同じ停留所を3周すれば3枚できる。**戸籍1:N（1停留所＝1カードにN観測）**と真っ向から衝突する。また「押下時点でどの停留所か決める」＝**廃止したはずの記録時吸着の復活**になる |
| **`timelapse_frame` に `is_marked` 真偽列を足す** | 結局スキーマ変更（同じ版鋳造）。しかも**カメラが止まっている回で押下が失われる**（実走で3セッションがカメラ0枚だった。#17 は77分・映像0枚）。イベント側に持つ方が堅い |
| **番兵カード（id=0「未同定」）を置いて NOT NULL を維持** | FK RESTRICT が実在行を要求するためカード表を汚す。集計・一覧・戸籍のすべてに例外が伝播する |
| **`poc_press_log.jsonl` をパス1 が直接読む** | JSONL は POC の計測物であって**データの正ではない**。バックアップ・機種変更・出自管理がすべて場当たりになる |

## 6. ★あわせて報告: v18 予約の前提が崩れている（**v20 とは別件**）

本件を調べる過程で、**2026-07-30 の官房裁定が置いた前提が現状と食い違っている**ことが分かった。

**裁定の内容**（`docs/2026-07-27_設計ドラフト_旧データ救済…` §3 追記）:
> `course_stop` 拡張の側が v19 へリナンバーされた。**本ドラフト（`navi_frame_index` 新設）の v18 予約はそのまま有効**
> ——**実装するときは v17 → v18（本ドラフト）→ v19（course_stop 拡張・既存）の順に挿し込む**。

**現状（実測）**:

- 実装は **`MIGRATION_17_19`（17→19 の直接ジャンプ）**。**v18 は意図的な穴**。
- **実機（OPPO）も実走2回目の複製DBも `user_version = 19`**——**既に v19 へ到達済み**。

**⇒ 「v17 → v18 → v19 の順に挿し込む」は、既に v19 に達した端末に対しては実行できない。**
v18 の migration を後から足しても、その端末は二度と通らない。

**裁定をお願いしたい点**: 旧データ救済ドラフトの版は、
**(a) 予約どおり v18 のまま**（＝新規インストールだけが通る穴として残す。既存端末には別途手当てが要る）か、
**(b) 実装時点の次番号へ繰り下げる**（＝v18 の穴は埋めない欠番として確定させる）か。

**当チームの意見は (b)**。理由は「**版番号は共有資源**であり、**通れない経路を予約として保持し続けると、
次に鋳造する者が毎回この判断をやり直す**」ため。ただし**先着の予約を後から動かす**ことになるので、
**原則（先着が番号を保つ・後発が動く）と衝突する**。だから当チームでは裁定しない。

> **⚠ この論点は v20 の可否とは独立している。** v20 は「今ある最大版 19 の次」を取るだけなので、
> v18 をどう扱っても v20 の番号は動かない。**v20 の鋳造を v18 の裁定待ちにしないでいただきたい。**

## 7. 版鋳造後にやること（Android チームの領分・参考）

版が下りたら当チームで実装する。**本起案の承認対象は版の鋳造のみ**で、以下は着手前に別途 `design-gate` を通す。

1. `stopCardId` を nullable 化＋`MIGRATION_19_20`（テーブル再作成）
2. POC の玄関が押下時に `stop_visit_event`（`trigger_type='MANUAL'`・`stop_card_id=NULL`・押下時の実測 lat/lon）を書く
3. デッドコード側の1箇所（§4）の扱いを決める（デッドコード975行の削除increment に合流させる案）
4. **コース創設が0件のときに理由を出す**（版とは独立に先行できる。§2 の誤解を防ぐ最小の手当て）

**検証の完了条件**: 実走で押下したセッションをコース創設で開き、**押下件数と同数の点が立つ**ことを実機で確認する
（「作れた」ではなく「**押した数と一致した**」を完了の意味にする）。
