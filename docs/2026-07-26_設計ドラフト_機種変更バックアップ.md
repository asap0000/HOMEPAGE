**起草**: 2026-07-26 / Android チーム
**前提**: 解釈ゲート（skill `design-gate`）実施済み。一枚絵＋非目標＋既定を提出し、**復唱1〜3はオーナー承認**。

## 0. 目的と非目的

**目的**: OPPO Reno3A を引退させるにあたり、旧機のデータを**1つの圧縮ファイル**にして USB メモリへ退避する。

**★★非目的「復元」を撤回する（オーナー決定 2026-07-27）**——**「全量バックアップも結局復元口が必要になった」**。
2026-07-26 時点では「作れるが戻せないアーカイブ」で足りると判断したが、**1日で覆った**。

> **なぜ覆ったか（記録として）**: 解釈ゲートの走行記が **「復元の口が無いと移行が完了しない」** を拾い、
> 復唱4行目に載せた。オーナーはそのとき「今回の増分には含めない」と判断したが、**翌日には必要になった**。
> **ゲートの指摘は正しく、判断のタイミングだけがずれていた**。走行記が拾った欠落は消えずに戻ってくる。

**復元が要る理由は現在3つある**（当初の1つから増えた）:
1. **機種変更**（旧機 → 新機）。当初の動機
2. **サルベージデータの復元先**——消失事故の救出アーカイブを **P50mini** へ載せる必要がある
3. **★環境分離との相互作用（2026-07-27 に新設された事情）**——`debug` / `field` のアプリ ID 分離を入れたため、
   **復元先は `field` 側（suffix 無し）でなければならない**。adb の手作業だと**間違って `debug` 側へ置く事故**が起きうる
   （分離の意味が消える）。**アプリ内の復元口なら、置き場所を間違えようがない**。

**この増分の範囲**: 「出口を作ってみる」は実装済み（`c4e35c0` 以降）。**復元は次の増分**として設計する（§8 未決5 を格上げ）。

> **【撤回前の記述・記録として残す】** 当初はこう書いていた——「この非目的が設計を1点で規定する: 本増分の成否は
> 『中身が完全であること』だけで測る（戻せることでは測れない）。戻す試験ができないぶん、中身の自己記述性
> （`manifest.json`）を厚くすることで将来の復元に備える」。
> **manifest を厚くした判断は結果的に正しかった**（復元の照合に使う）が、**「戻す試験ができない」という前提は1日で消えた**。

**★出口の増分の範囲＝「出口を作ってみる」まで（オーナー決定 2026-07-26・実装済み）**。
ボタン → 棚卸し → ZIP 生成 → SAF で保存、の一本を通す。**復元・暗号化・分割・恒久的なバックグラウンド実行は入れない**。
長時間処理の走らせ方（未決1）は**実測サイズを得てから決める**——最小の出口は前景（画面を開いたまま）で動かし、
そこで得た実測値をもって §6 の 4GB 判断と合わせて恒久策を決める。**測る前に仕組みを作らない**。

### ★消費者は2人いる（2026-07-26 追記・当初の想定が誤っていた）

当初これを「作れるが戻せない死蔵アーカイブ」と位置づけたが、**誤りだった**。Windows チームの登記簿にすでに次がある:

- **プランナーEX の出島 IMPORT は `.zip` を受け付ける**（`dejima.py:41` が `.zip`/`.isnavi`/`.json` を許可。`.gpx` は弾く）。
  **門は既に開いており、無いのは「中身を読んで断片にするコンバータ」の方**（Windows STATE）。
- Windows STATE に **「スマホから全量バックアップを `.zip` で取得すれば、プランナーは自由にデータ加工できる」** と明記されている。
- **USB は N:N 運搬モデル**として登記済み——**App のインストール元＋EX の可搬ランタイム＋N台分のデータ回収コンテナ**。
  プランナーEX は **USB メモリの中だけで完結して動く**（オーナー）。

したがって本ファイルは **①端末の退避アーカイブ** であると同時に **②プランナーEX への一次素材の供給路** である。
**コース全体 GPX エクスポートを撤去した判断（`c4e35c0`）と表裏**——EX への提供口は**この `.zip` 全量に一本化された**。

**実運用の含意**: 現在の実車データは**4台（バス）のうち2台分**。**残り2台分も同じ OPPO で取得しうる**——ただしこれは**開発中の話**で、
**実運用の N:N は USB メモリが担う**（オーナー 2026-07-26。当初「残りは別端末にある」と読んだのは起草者の誤り）。
いずれにせよ**同じ USB に複数端末・複数世代のファイルが並ぶことは運搬モデルの前提**であり、
§2 の命名（`originId`＋`gen` で衝突しない）はここに噛み合う。

### 背景（オーナーが示した見通し・設計の前提）

- 端末データは3層に分かれる。**①撮り直せないもの**（停留所カードの写真・音声、走行記録の GPS と映像コマ）
  **②作り直せるもの**（簡易版ナビ用マップ＝コース定義から `NaviMapGenerator` が自己生成）
  **③PC から来るもの**（`.iscmap`、将来の `.isnavi`）。
- **EX 版ナビの取り込み口ができれば、端末は「EX ナビ再生機」として復活できる**＝②③は復元不要になる。
- プランナー EX のスタンドアロン化でコース設計が PC 側へ移れば、**端末はマスタから「再生機＋記録機」へ**役割が移り、
  守るべきは①だけになる。**復元の要否は「いつ EX の取り込み口ができるか」に従属する**。

## 1. 棚卸し（何を入れ、何を入れないか）

| 対象 | 実体の場所 | 入れる | 理由 |
|---|---|:--:|---|
| Room DB 本体 | `getDatabasePath("buscourse.db")` | ○ | すべての索引。コース・停留所・**ナビ用マップ**（`navi_map`/`navi_segment`/`navi_track_point`）を含む |
| DB の WAL / SHM | 同 `-wal` / `-shm` | ○ | **3点セット必須**。取りこぼすと古い状態を読む（2026-07-14 の実害） |
| 停留所カードの写真・音声 | `files/buscourse/stopcards/**` | ○ | 撮り直せない |
| 走行記録 | `files/buscourse/sessions/**`（`meta.json`・`gps_raw.jsonl`・`frames/`） | ○ | 走り直せない。**総量の大半を占める** |
| 区間軌跡 | `files/buscourse/segments/*.gpx` | ○ | **地図の経路描画がこれを読む**（`RouteTrackOverlay`）。**かつプランナーEX が「断片」として食う一次素材**——EX は試走 GPX の断片を大量・順不同・重複・失敗込みで取り込み、エディタでつなぎ合わせて直線を実車軌跡に置き換える（Windows STATE） |
| 映像ナビ設定 | `files/datastore/navi_settings.preferences_pb` | ○ | 作り直すのが面倒 |
| 比較データの残骸 | `files/buscourse/comparisons/**` | ○※ | v14 で比較3テーブルは drop 済みだが**ファイルが残っている可能性**がある。小さいので入れて判断を後回しにする（**未決2**） |
| 地図パッケージ | `files/buscourse/maps/**` | ✕ | `.iscmap` の展開物。**PC で作り直せる**。タイル群で巨大 |
| 記録中の一時状態 | `files/datastore/recording_state.preferences_pb` | ✕ | 移行先で意味を持たない |
| 書き出し済み GPX | （`exports/` は廃止済み） | ✕ | 旧仕様の残骸（オーナー裁定・`c4e35c0` で機能自体を撤去） |

**移行が成立する前提の確認**: DB には**相対パスしか保存されていない**（`BusCourseStorage` の規約。`File(filesDir, "buscourse/<relPath>")` で実行時解決）。
したがって端末が変わってもパスが壊れない。**ここが絶対パスだったら移行そのものが成立しなかった**。

## 2. ファイル名のきまり

```
buscourse_<originId>_<gen>_<yyyyMMdd-HHmm>.zip
例: buscourse_k7m2x9_0007_20260726-1432.zip
```

| 部分 | 意味 | 決め方 |
|---|---|---|
| `originId` | **出自**＝端末のしるし。6文字（英小文字＋数字） | **初回起動時に一度だけ生成**して DataStore に保存。以後不変 |
| `gen` | **世代**＝その端末で何回目か。4桁ゼロ埋め | 押すたびに +1。DataStore に保存。**時計が狂っても順序が分かる** |
| `yyyyMMdd-HHmm` | **いつ**。端末ローカル時刻 | 人が読むため |
| `.zip` | 素の ZIP。**PC でそのまま開ける** | パスワードなし（オーナー指示） |

**他機と重複しない理由**: `originId` が端末ごとに違うため、同じ USB に複数端末のファイルが並んでも名前が衝突しない。
同一端末内は `gen` が単調増加するので上書き事故も起きない。

**★外部の端末識別子は取得しない**（`ANDROID_ID`・IMEI 等）。アプリが自分で生成した符号だけを使う
（オフライン厳守の精神とプライバシー配慮。個体識別子を持ち出さない）。

**★将来復元を作るときの規則**: **復元先の端末は自分の `originId` を新規生成し、復元元の `originId` は
`manifest.json` の「由来」として残す**。引き継いでしまうと2台が同じ `originId` を名乗り、上記の非重複性が崩れる。

## 3. 中身の構造

```
buscourse_k7m2x9_0007_20260726-1432.zip
├─ manifest.json                    ← 自己記述。将来の復元の鍵
├─ db/
│   ├─ buscourse.db
│   ├─ buscourse.db-wal
│   └─ buscourse.db-shm
└─ files/
    ├─ buscourse/stopcards/…  sessions/…  segments/…  comparisons/…
    └─ datastore/navi_settings.preferences_pb
```

`manifest.json` に持たせるもの:

- バックアップ形式の版（**未決1** 参照）
- `originId` / 由来 `originId`（初回は空）/ `gen` / 作成時刻
- アプリのバージョン名・バージョンコード / **DB スキーマ版**
- **含めたものと除いたものの一覧**（除外は理由つき。「地図は PC から入れ直す」等）
- ファイル総数・総バイト数 / ZIP 全体の SHA-256

> **なぜ manifest を厚くするか**: 今回は復元を作らないため、**このファイルだけが「何が入っているか」の唯一の証言**になる。
> 復元を作るのが半年後になっても読み解けるように、機械可読な形で残す。

## 4. 操作の流れ

1. メニューから **「バックアップ」**
2. **確認画面** — 含むもの／含まないもの／**推定サイズ**／保存先の空き容量
3. **「保存先を選ぶ」** → SAF `ACTION_CREATE_DOCUMENT`（USB メモリを選べる）
4. **進捗** — 処理したファイル数とバイト数
5. **完了** — できたファイル名・サイズ・SHA-256 を表示（PC 側で照合できるように）

---

## 5. 既定で守ること

- **記録中は実行しない**。ボタンを無効化し、理由を表示する（記録中の DB を固めると壊れる）
- **DB は WAL チェックポイント（FULL）してから固め、3点セットで入れる**
- **失敗したら半端なファイルを残さない**（SAF の出力先を削除する）
- 進捗中に画面を離れても処理は続く（**未決1**）
- 外部ネットワークへは一切出さない（オフライン厳守。ローカルの USB 書き出しのみ）

---

## 6. 4GB 問題（FAT32 の壁）

FAT32 の USB メモリは**1ファイル 4GB が上限**。`sessions/frames` が大きいと ZIP が超えうる。

**方針: まず旧機の実データ量を測ってから決める。** 超えないなら分割機構は作らない
（**使わない仕組みはバグの温床**）。測る手段は実装の副産物として手に入る——確認画面の推定サイズがそれである。
超えることが分かった時点で、分割か exFAT 前提かを選ぶ（**未決3**）。

## 7. 検証

**純計算（単体テスト）**
- 命名: `gen` の単調増加・`originId` の書式・同一端末で名前が衝突しないこと
- 棚卸し: include / exclude の判定（パスを与えて可否が返る純関数に切る）
- `manifest.json` の内容（版・件数・除外理由）

**実機**
- WAL チェックポイント後に DB が読めること（固めた 3 点セットを PC の sqlite3 で開く）
- 実機で1回作り、**PC でそのまま ZIP として開けること**
- 記録中はボタンが押せないこと

## 8. 未決事項（着手前に決める）

1. **長時間処理の走らせ方** — WorkManager（一回限り）か Foreground Service（`dataSync`）か。
   数 GB のコピーになるため、画面を離れても続く必要がある。**オフライン厳守には抵触しない**（ローカル I/O のみ）。
2. **`comparisons/` を入れるか** — v14 で比較3テーブルは drop 済み。ファイルの残骸が実際にあるか要確認。
3. **4GB 超の扱い** — §6 のとおり実測後に決める。
4. **★形式の版を鋳造するのか、しないのか（Windows と先に擦り合わせる）** — **当初「Android 単独消費」と書いたのは誤りで、撤回する**（§0 追記参照）。
   プランナーEX が第二の消費者であり、**交換フォーマット版は共有資源**（ルート CLAUDE.md）・**版の鋳造は官房へ上げる4点のひとつ**（CHARTER §5）。
   ただし**鋳造が本当に要るかは自明でない**——EX の出島 IMPORT は既に `.zip` を通し、**中身を読むコンバータは EX 側が書く**と登記されている。
   その形なら**版を名乗らず、`manifest.json` の項目を Windows と合意するだけで足りる**可能性がある。
   **順序**: ①Windows へ「EX が何を読めれば断片化できるか／版を要るか」を確認 → ②要るなら官房へ鋳造を上げる。**先に名乗らない**。
5. **復元** — **次の増分として設計する（2026-07-27 格上げ・§0 参照）**。設計の要点は次のとおり。
   - **入口は1つだけにする**——受け付けるのは**本バックアップ形式の `.zip` のみ**。
     **救出アーカイブ（tar＋DB の寄せ集め）は PC 側でバックアップ形式に詰め直してから渡す**。
     アプリに2種類の入口を作らない（片方が必ず腐る）。
   - **復元先は `field` 側**（環境分離。アプリ内から復元すれば置き場所を間違えようがない＝これが3つ目の動機）。
   - **まっさらな端末への復元のみを既定**とする。既存データがあるときは**黙って混ぜない**——拒否するか、明示的な上書き確認を出す。
   - **DB 版の差はマイグレーションに任せる**。救出 DB は v12、現行は v17。**エミュレータで v12→v17 が通ることは実測確認済み**
     （12テーブルの行数が移行前後で完全一致・2026-07-26）。
   - **復元後に照合する**——`manifest.json` の SHA-256 とファイル数で、入ったものが出したものと同じことを確かめる。
     **戻せたと言い切るには照合が要る**（今回の「作れるが戻せない」を繰り返さない）。

6. **★セキュリティ方針が未定である（2026-07-26・オーナーが明示的に留保）** — 「今回あえてセキュリティ問題に触れていない。
   **パスワード運用なのか暗号化なのか**」（オーナー）。**「パスワード不要」は今回の実装指示であって、方針の決定ではない**。
   中身は**園児の停留所・写真・GPS 軌跡＝PII** であり、それが**素の ZIP で USB に載って持ち歩かれる**。
   Windows STATE も §13-2 で「暗号化＝漏洩対策」を論点として登記している。**運用に乗せる前に決める必要がある**。

7. **★USB を「ドングル」として同定する構想（要 Windows・オーナー発案 2026-07-26）** — **バックアップ先の USB に EX がいる**なら、
   その媒体が**正規のものだと同定できる**。すなわち「**この USB は書き込んでよい相手か**」を判定するゲートが成立する。
   パスワードや暗号化の代わりに——あるいはそれに加えて——**媒体の同定によって流出面を狭める**方向。
   **本ドラフトには方式を書かない**。EX 側が何をもって「自分がいる」と示せるか（署名ファイル・既知の構造・鍵）を
   **Windows チームと詰めてからでないと書けない**（オーナー指示）。増分としても先の話。
