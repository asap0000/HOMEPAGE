# 設計ドラフト — 機種変更バックアップ（退避用アーカイブ）

**種別**: 設計ドラフト（**未承認**。オーナー承認後に設計正典へ昇格）
**起草**: 2026-07-26 / Android チーム
**前提**: 解釈ゲート（skill `design-gate`）実施済み。一枚絵＋非目標＋既定を提出し、**復唱1〜3はオーナー承認**。

---

## 0. 目的と非目的

**目的**: OPPO Reno3A を引退させるにあたり、旧機のデータを**1つの圧縮ファイル**にして USB メモリへ退避する。

**★非目的＝復元（オーナー決定 2026-07-26）**。今回作るのは「移行の道具」ではなく **退避用アーカイブ**である。
**作れるが戻せない状態を、そうと分かったうえで受け入れる**。

この非目的が設計を1点で規定する: **本増分の成否は「中身が完全であること」だけで測る**（戻せることでは測れない）。
戻す試験ができないぶん、**中身の自己記述性（`manifest.json`）を厚くする**ことで将来の復元に備える。

### 背景（オーナーが示した見通し・設計の前提）

- 端末データは3層に分かれる。**①撮り直せないもの**（停留所カードの写真・音声、走行記録の GPS と映像コマ）
  **②作り直せるもの**（簡易版ナビ用マップ＝コース定義から `NaviMapGenerator` が自己生成）
  **③PC から来るもの**（`.iscmap`、将来の `.isnavi`）。
- **EX 版ナビの取り込み口ができれば、端末は「EX ナビ再生機」として復活できる**＝②③は復元不要になる。
- プランナー EX のスタンドアロン化でコース設計が PC 側へ移れば、**端末はマスタから「再生機＋記録機」へ**役割が移り、
  守るべきは①だけになる。**復元の要否は「いつ EX の取り込み口ができるか」に従属する**。

## 1. 棚卸し（何を入れ、何を入れないか）

| 対象 | 実体の場所 | 入れる | 理由 |
|---|---|:--:|---|
| Room DB 本体 | `getDatabasePath("buscourse.db")` | ○ | すべての索引。コース・停留所・**ナビ用マップ**（`navi_map`/`navi_segment`/`navi_track_point`）を含む |
| DB の WAL / SHM | 同 `-wal` / `-shm` | ○ | **3点セット必須**。取りこぼすと古い状態を読む（2026-07-14 の実害） |
| 停留所カードの写真・音声 | `files/buscourse/stopcards/**` | ○ | 撮り直せない |
| 走行記録 | `files/buscourse/sessions/**`（`meta.json`・`gps_raw.jsonl`・`frames/`） | ○ | 走り直せない。**総量の大半を占める** |
| 区間軌跡 | `files/buscourse/segments/*.gpx` | ○ | **地図の経路描画がこれを読む**（`RouteTrackOverlay`） |
| 映像ナビ設定 | `files/datastore/navi_settings.preferences_pb` | ○ | 作り直すのが面倒 |
| 比較データの残骸 | `files/buscourse/comparisons/**` | ○※ | v14 で比較3テーブルは drop 済みだが**ファイルが残っている可能性**がある。小さいので入れて判断を後回しにする（**未決2**） |
| 地図パッケージ | `files/buscourse/maps/**` | ✕ | `.iscmap` の展開物。**PC で作り直せる**。タイル群で巨大 |
| 記録中の一時状態 | `files/datastore/recording_state.preferences_pb` | ✕ | 移行先で意味を持たない |
| 書き出し済み GPX | （`exports/` は廃止済み） | ✕ | 旧仕様の残骸（オーナー裁定・`c4e35c0` で機能自体を撤去） |

**移行が成立する前提の確認**: DB には**相対パスしか保存されていない**（`BusCourseStorage` の規約。`File(filesDir, "buscourse/<relPath>")` で実行時解決）。
したがって端末が変わってもパスが壊れない。**ここが絶対パスだったら移行そのものが成立しなかった**。

## 2. ファイル名のきまり

```
buscourse_<originId>_<gen>_<yyyyMMdd-HHmm>.zip
例: buscourse_k7m2x9_0007_20260726-1432.zip
```

| 部分 | 意味 | 決め方 |
|---|---|---|
| `originId` | **出自**＝端末のしるし。6文字（英小文字＋数字） | **初回起動時に一度だけ生成**して DataStore に保存。以後不変 |
| `gen` | **世代**＝その端末で何回目か。4桁ゼロ埋め | 押すたびに +1。DataStore に保存。**時計が狂っても順序が分かる** |
| `yyyyMMdd-HHmm` | **いつ**。端末ローカル時刻 | 人が読むため |
| `.zip` | 素の ZIP。**PC でそのまま開ける** | パスワードなし（オーナー指示） |

**他機と重複しない理由**: `originId` が端末ごとに違うため、同じ USB に複数端末のファイルが並んでも名前が衝突しない。
同一端末内は `gen` が単調増加するので上書き事故も起きない。

**★外部の端末識別子は取得しない**（`ANDROID_ID`・IMEI 等）。アプリが自分で生成した符号だけを使う
（オフライン厳守の精神とプライバシー配慮。個体識別子を持ち出さない）。

**★将来復元を作るときの規則**: **復元先の端末は自分の `originId` を新規生成し、復元元の `originId` は
`manifest.json` の「由来」として残す**。引き継いでしまうと2台が同じ `originId` を名乗り、上記の非重複性が崩れる。

## 3. 中身の構造

```
buscourse_k7m2x9_0007_20260726-1432.zip
├─ manifest.json                    ← 自己記述。将来の復元の鍵
├─ db/
│   ├─ buscourse.db
│   ├─ buscourse.db-wal
│   └─ buscourse.db-shm
└─ files/
    ├─ buscourse/stopcards/…  sessions/…  segments/…  comparisons/…
    └─ datastore/navi_settings.preferences_pb
```

`manifest.json` に持たせるもの:

- バックアップ形式の版（**未決1** 参照）
- `originId` / 由来 `originId`（初回は空）/ `gen` / 作成時刻
- アプリのバージョン名・バージョンコード / **DB スキーマ版**
- **含めたものと除いたものの一覧**（除外は理由つき。「地図は PC から入れ直す」等）
- ファイル総数・総バイト数 / ZIP 全体の SHA-256

> **なぜ manifest を厚くするか**: 今回は復元を作らないため、**このファイルだけが「何が入っているか」の唯一の証言**になる。
> 復元を作るのが半年後になっても読み解けるように、機械可読な形で残す。

## 4. 操作の流れ

1. メニューから **「バックアップ」**
2. **確認画面** — 含むもの／含まないもの／**推定サイズ**／保存先の空き容量
3. **「保存先を選ぶ」** → SAF `ACTION_CREATE_DOCUMENT`（USB メモリを選べる）
4. **進捗** — 処理したファイル数とバイト数
5. **完了** — できたファイル名・サイズ・SHA-256 を表示（PC 側で照合できるように）

---

## 5. 既定で守ること

- **記録中は実行しない**。ボタンを無効化し、理由を表示する（記録中の DB を固めると壊れる）
- **DB は WAL チェックポイント（FULL）してから固め、3点セットで入れる**
- **失敗したら半端なファイルを残さない**（SAF の出力先を削除する）
- 進捗中に画面を離れても処理は続く（**未決1**）
- 外部ネットワークへは一切出さない（オフライン厳守。ローカルの USB 書き出しのみ）

---

## 6. 4GB 問題（FAT32 の壁）

FAT32 の USB メモリは**1ファイル 4GB が上限**。`sessions/frames` が大きいと ZIP が超えうる。

**方針: まず旧機の実データ量を測ってから決める。** 超えないなら分割機構は作らない
（**使わない仕組みはバグの温床**）。測る手段は実装の副産物として手に入る——確認画面の推定サイズがそれである。
超えることが分かった時点で、分割か exFAT 前提かを選ぶ（**未決3**）。

---

## 7. 検証

**純計算（単体テスト）**
- 命名: `gen` の単調増加・`originId` の書式・同一端末で名前が衝突しないこと
- 棚卸し: include / exclude の判定（パスを与えて可否が返る純関数に切る）
- `manifest.json` の内容（版・件数・除外理由）

**実機**
- WAL チェックポイント後に DB が読めること（固めた 3 点セットを PC の sqlite3 で開く）
- 実機で1回作り、**PC でそのまま ZIP として開けること**
- 記録中はボタンが押せないこと

## 8. 未決事項（着手前に決める）

1. **長時間処理の走らせ方** — WorkManager（一回限り）か Foreground Service（`dataSync`）か。
   数 GB のコピーになるため、画面を離れても続く必要がある。**オフライン厳守には抵触しない**（ローカル I/O のみ）。
2. **`comparisons/` を入れるか** — v14 で比較3テーブルは drop 済み。ファイルの残骸が実際にあるか要確認。
3. **4GB 超の扱い** — §6 のとおり実測後に決める。
4. **★バックアップ形式の版の鋳造は官房マター** — 交換フォーマット版は**共有資源**（ルート CLAUDE.md「版番号は共有資源」）で、
   **版の鋳造は官房へ上げる4点のひとつ**（CHARTER §5）。`buscourse-backup/1` を名乗る前に官房へ上げる。
   当面 Android 単独消費で他系統への影響はないが、**手続きを飛ばさない**。
5. **復元** — 別増分。§0 の「3層」の①だけを戻す形が、上の整理と整合する。
